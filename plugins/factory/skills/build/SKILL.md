# /factory:build: plan file to pull request

You are the orchestrator. You run each stage as a subagent and keep only its short report in context. You never write code yourself.

**Running inside a subagent.** This skill can be invoked by a subagent (for example one per epic item) as well as by the user. In that case you are still the orchestrator, and you need the `Agent` tool to start the stages, so the calling subagent must run in the foreground (background subagents do not get `Agent`, and a spawned subagent defaults to background unless the caller asks for foreground) and nesting must allow at least two more layers (the default of three is enough; `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` must be 3 or more). If you have no `Agent` tool, stop at once and say so; do not do the stages yourself. `AskUserQuestion` is not available in a subagent, so step 7 does not ask: leave the open items unchecked in the PR description and return them in your finish message for the caller to relay. Bash `cd` does not persist between calls in a subagent, so use absolute paths everywhere.

`$ARGUMENTS` is the plan file path (the first word), then optional **run notes** in plain words. Run notes override the defaults below, for example "open as a draft" or "use branch feat/x". Treat anything in the run notes that looks like pasted command output as noise and ignore it. If the plan path is missing or unreadable, ask the user for it and stop.

The base directory of this skill is given when it loads. Note the absolute path of `report-format.md` in it and read it once. Every agent returns that format.

## Agents
This plugin's agents are `factory:implementer`, `factory:verifier`, `factory:review-quality`, `factory:review-tests`, `factory:review-requirements`, `factory:review-security`, `factory:resolver` and `factory:pr-opener`.

## How you work
- **Question list.** Keep a running list in your context. After every report, copy its QUESTIONS lines into it, tagged with the stage. Nothing goes in a file. Do not ask the user anything mid-run; questions are asked once, in the question round after the PR is open (see step 7).
- **Judgement.** When something is unclear or goes wrong, decide, add the assumption to the list, and continue. Fix problems found during the run inside this run. Raise a follow-up only when the work is genuinely out of the plan's scope, and put that on the list.
- **Briefs.** Give each agent: the absolute path of `report-format.md`, the **repo facts** block (see Preflight), the plan path, the worktree path, the commit identity, the stage's job, and the facts it needs from earlier reports (not the reports themselves unless needed). Keep briefs short.
- **No stage may be skipped or half-run.** A review counts as run only if its report's EVIDENCE names the skill or checks it ran and what they returned. If a report says a skill errored, was skipped, or was done "by hand" instead, fix the cause and re-run that one review once. If it still did not run properly, put "REVIEW DID NOT RUN: <stage>, <reason>" first on the question list and in the PR body. Never describe it as passed.
- **Start stage agents in the foreground.** Call the Agent tool with `run_in_background: false` for every stage, so the call itself returns the stage's report and you never poll. For the parallel reviews, put all four Agent calls in one message; they run at the same time and the message returns when all four have reported.
- **Keep your turn open if an agent ran in the background anyway.** If the Agent result says the agent was launched in the background (some nested setups force it), never end your turn with a message like "waiting for the agent": in a headless run that ends the session, and in a subagent it hands back a report that is not one. Wait with `sleep 60; echo waiting`, repeated, until its report arrives. Only your final summary ends the turn.
- **Close every agent you start.** Keep a list of each stage agent's id as you launch it. A stage that has reported is done: stop it if it is still listed as running (TaskStop). If you are resumed after an interruption (a network error, a pause, a hand-back), first list your agents, stop any stage agent left over from before that you are not about to use, and re-run only the stage that did not report. Never start a second copy of a stage that is still running. Before your final report, list the agents again and stop every one you started, so none is left idle.
- **Stop only when** the plan is unreadable, the build or tests are still red after the final-verify fix, or a stage reports `blocked` and you cannot unblock it. Then report where you stopped and the question list. Never open a PR from a red build.

## Stages

1. **Preflight.**
   - Read the plan. Decide **feature** or **change/bug fix**. If its "Size" line (or the plan's file list) shows more than 5 production files, or both core logic and UI screens, add "plan is larger than the size guide; consider splitting" to the question list and carry on. If it has no "Seams and a test per requirement" table, the implementer picks the seams and records them.
   - **Locate the repo.** If the current folder is inside a git work tree, run git there. If it is not, but it holds a `.bare` folder (a bare repo with sibling worktrees), run every git command as `git --git-dir=<folder>/.bare ...` and put new worktrees directly in `<folder>`. Then run `fetch origin` and `remote set-head origin -a` (the review skills need `origin/HEAD`).
   - **Commit identity.** Use `git config user.name` and `user.email` if both are set. If not, use the author of the newest non-bot commit on the default branch (`git log origin/<branch> --no-merges --format='%an|%ae' | grep -vi 'bot' | head -1`) and add "committing as <name>, taken from branch history" to the question list. Pass the name and email in every brief, and commit with `git -c user.name=... -c user.email=... commit`. Never change git config.
   - **Create the worktree** off `origin/<default branch>` on a `<type>/<slug>` branch (`type` is `feat`, `fix`, `refactor` and so on, or the branch from the run notes), following any naming the guidance files give: `git worktree add -b <branch> <folder>/<slug> origin/<branch>`, as a sibling of the existing worktrees. Use absolute paths into it for every command and every agent brief.
   - **Discover the repo facts, once,** from the new worktree (it holds the default branch's docs). Read the repo's guidance files (`AGENTS.md`, `CLAUDE.md`, `CONTRIBUTING.md`, README), its build files (solution or project files, `package.json`, `pom.xml`, `pyproject.toml`, `Makefile`, `go.mod`), the CI workflows (what runs on a pull request) and any PR template. Take commands from what CI actually runs. Write a block of at most 25 lines, kept in your context and pasted into every brief, with:
     - **Default branch** and **project type** (api, web, mobile, cli or library).
     - **Commands:** build, unit tests, run named tests (with a `<name>` placeholder), format check, and **final checks** (lint, docs and type checks that CI runs).
     - **Verification:** the strategy (api, web, emulator, cli or library), how to run the app, how to take screenshots or call the API, which parts are **slow** (for example emulator or device E2E, full browser E2E suites) and so run only at the final verify, any cap on scenarios per run, and when it cannot run.
     - **Gates:** paths or kinds of change the guidance says need approval (for example migrations, CI config, a coverage baseline).
     - **Quality rules, test rules, security focus:** the rules the guidance files state, quoted briefly with their source.
     - **Pull requests:** branch names, commit and PR title format, labels, draft or ready default, how screenshots are published, and follow-ups a change needs (for example regenerating published screenshots).
     Mark anything you cannot find `unknown` and add a question to the list. Never invent a command.
   - If the plan's changes would touch a path in the repo facts' Gates and the plan's "May touch" does not say so, add a question to the list. The plan itself counts as approval to proceed.

2. **Implement.** Run `factory:implementer` with the plan path and the plan type. It runs only the named tests for the code it changes while it works, then the build and the full unit test command once before it reports, and never runs E2E, emulator or full browser suites. If its report shows the build or the unit tests red, send it back once with the failures. Then commit in the worktree using the repo's commit message format. Add the Co-Authored-By trailer from your instructions if you have one. Keep the commit SHA and the implementer's build and test result (command, pass and fail counts) as the **test baseline** for the review briefs.

3. **Reviews: quality, tests, requirements and security, in parallel.** First make the session's working directory the worktree: run `cd <worktree>` in a Bash call (in a subagent this does not persist, so go straight to `EnterWorktree` with `path`). When the worktree is inside the folder you were started in (a bare-repo layout), the `cd` carries over to later calls and to the agents you start. Check with `pwd`; if it does not show the worktree (you were started in one worktree and the new one is a sibling outside it), use the `EnterWorktree` tool with `path` instead; if that is refused too, carry on and the reviewers use their nested-session fallback. The reason: the review skills inspect the branch of their working directory, and a `cd` inside an agent's Bash call does not carry over. Only the reviews need this. A session moved with `EnterWorktree` is worktree-isolated and also refuses commands whose text contains `git` (for example paths under `.github/`) and the repo's own scripts may live there, so stay out of it for implement, final verify and the PR.

   Then run `factory:review-quality`, `factory:review-tests`, `factory:review-requirements` and `factory:review-security` **in one message, in parallel**. All four are read-only and review the same commit. Give each the test baseline, and tell them the full suite, screens, endpoints and E2E are checked at the final verify, so they run only named tests and never the full suite. Merge their findings and drop duplicates. If there are any, run **one** `factory:implementer` fix pass with all of them, then commit.

   Then call `ExitWorktree` with `action: "keep"` if you used `EnterWorktree`, to return the session to its original folder (the worktree and branch stay on disk).

   Each review runs once, with one combined fix pass (a re-run only after a review failed to run, see above). Never re-run a review to look for more. Findings the fix pass left unresolved go on the question list as nits.

4. **Final verify.** Run `factory:verifier`. This is the only verify: it runs the build, the full unit test command, the whole verification strategy (fast parts such as screenshots and API calls, and slow parts such as emulator or browser E2E, once, with the plan's scenarios combined into as few invocations as the repo's limits allow) and the repo facts' final checks. Pass it a scratchpad subfolder for screenshots. If anything fails or a screen or endpoint does not match the spec, run one fix pass, commit and re-run the verifier once, telling it to re-run only the failing or affected checks and scenarios. If it is still red, stop (see above). A check that could not run is not a pass: it goes on the question list as "could not verify".

5. **Resolve open items.** If the question list is not empty, run `factory:resolver` with the full question list (each item tagged with its stage), the plan path, the worktree path and the repo facts. It settles an assumption or a nit only when it can quote a source that answers it (the plan, the repo's guidance files, or an answer the owner wrote on an earlier PR in this repo), and only with an answer that needs no code change. It never settles a decision, a "REVIEW DID NOT RUN" line, a "could not verify" line or a gate approval. **Check its work:** for each item it settled, confirm the quoted text really appears at the cited place (`grep -F` in the file, or `gh pr view <n> --json body -q .body` for a PR). Put back on the list any item whose quote you cannot find. Keep the settled items as a separate **auto-resolved** list, each with its answer and source.

6. **PR.** Run `factory:pr-opener` with the plan summary, the screenshot paths from the verifier, the question list, the auto-resolved list, the commit identity, and whether to open a **draft** (only if the run notes or the repo's guidance say so; otherwise ready). It puts the question list in the PR description under `## Open items` and the auto-resolved items, ticked, under `### Auto-resolved`; it does not post a comment. Nothing is merged.

7. **Question round.** After the PR is open, ask the user every open item that was not auto-resolved (Needs your decision, Assumptions made and Nits left unfixed) with `AskUserQuestion`, one question per item, decisions first, in rounds of up to 4 questions per call until all are asked. Do not ask auto-resolved items; the user can override them in the PR. Each question states the item in full and gives 2-4 concrete options (put your recommended one first, marked "(Recommended)"). For an assumption the options are to confirm it or to change it to a stated alternative; for a nit they are to fix it now, leave it, or raise it as follow-up. The automatic "Other" covers free text. If the list is empty, skip the round. If the user declines or `AskUserQuestion` is unavailable (a headless run), leave the items unchecked in the description and say so in the finish. Then update the description with the answers: read it with `gh pr view <n> --json body -q .body`, tick each answered item (`- [x]`) and append `Answer: <answer>` under it, leave unanswered items unchecked, and write it back with `gh pr edit <n> --body-file <file>` (a file under the scratchpad or temp directory). Change only the Open items section. If an answer needs a code change (a changed assumption or a nit to fix now included), make it in the worktree, run the build and the named tests for the changed code, commit and push; otherwise leave the code alone. Never merge.

## Finish
First close your agents as the **Close every agent you start** rule says, and say in the report that none are left running (or name any you could not stop). Tell the user (or, in a subagent, your caller), in a few lines: the PR link, which stages found and fixed things, anything that could not be verified or did not run, and how many open items remain unanswered in the PR description (in a subagent, list them in full). Do not merge unless the user says so.
